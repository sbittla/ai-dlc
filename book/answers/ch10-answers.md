## Recall

**1. Workflow and agent.** In a workflow, code decides the sequence of steps and calls a model at fixed points for one bounded job; the model never chooses the next step. In an agent, the model chooses its own next action from what it has observed, until it decides it is done, while code still executes every action and decides whether the run may continue. For the helper, finding a file that the task did not list, and that no listed file imports, needs an agent's choice: which name to search for and which result to read. Deciding whether to stop, and whether a pull request may open, should never be the model's decisions: code decides them in every Relay design. In the workflow, code also decides when to run the tests and the pre-review check; in the single agent the model chooses when to call `run_tests`, but the boundary runs it and the done check decides whether the result counts. Deduct for answers that call any loop with a model an "agent" without saying who chooses the next step.

**2. Stopping conditions.** In order: the budget (`budget:steps`, `model_calls`, `usd` or `seconds`, whichever limit is reached first in that order), then a repeated failure signature (`repeated_failure:<signature>`, three times), then no progress (no new state in the last six steps). The reviewer's approval is not a stopping condition because it is decided by a model inside the loop: a model that keeps asking for the same change cannot be relied on to notice that it is looping, and in the incident it never did. A stopping condition must be checked by code, before each step, from the budget and the run's history. Full marks name the order and the reason.

**3. Write-ahead intent.** A record, written before a step's effect, that the step is about to run, completed as `ok` or `error` after it. On resume, a step found `started` has an unknown outcome. Relay's boundary runs it again only if its contract declares an idempotent handler (`open_pull_request`, whose handler looks for an open pull request on the branch first); otherwise it refuses with `unknown_outcome` and the run stops for a person. The answer depends on the handler because only the handler can know whether repeating the effect is safe: the journal cannot see whether GitHub created the pull request before the process died. Credit answers that note GitHub's own refusal of a duplicate open pull request, with the caveat that the handler should not rely on it alone.

**4. Trajectory evaluation.** It measures the steps an agent took, not only its result: which tools it called and in what order, refusals, repetitions, cost, and whether every high-impact action was approved first. Examples from Table 10.13 (any two): the single agent's 83 `invalid_args` and 4 `path_not_allowed` refusals; the multi-agent design's 846 repeated reads of the same file in a run; 36.5 steps per run for the multi-agent design against 12.5 for the workflow; every pull request in all 1,080 runs approved first, read from the audit trails. An outcome evaluation would score two runs that open the same correct pull request identically, whatever they cost or attempted.

## Apply

**5. Budget arithmetic.** Call k sends 50,000k input tokens and writes 500.
- (a) Without caching, call k costs 50,000k × $4 / 10⁶ + 500 × $20 / 10⁶ = $0.2k + $0.01. After three calls the run has spent $0.21 + $0.41 + $0.61 = **$1.23**, in 6 steps. Call 4's estimate is $0.80 + 2,048 × $20 / 10⁶ = $0.84096, and $1.23 + $0.84 = $2.07 exceeds $2.00, so `admit` refuses it: **3 model calls, $1.23, stopped by `budget:usd`**. The step limit (40) is never close.
- (b) With caching, call k pays 50,000 fresh tokens at $4 per million and 50,000(k − 1) cached at $0.20 per million: $0.21 + $0.01(k − 1). The calls cost $0.21, $0.22, … $0.28, a total of **$1.96** after eight calls, in 16 steps. Call 9's estimate is $0.20 + $0.08 + $0.04096 = $0.32, and $1.96 + $0.32 exceeds $2.00: **8 model calls, $1.96, `budget:usd`**.
- A strong answer notes that `admit`'s upper estimate stopped both runs with money left ($0.77 and $0.04), and that the same budget buys more than twice as many calls with caching. It also notes that the check happens before the call, on the estimate: in (a) the fourth call is refused on its estimate of $0.84, without needing to know its real cost of $0.81. Deduct for answers that run a call first and check the budget afterwards.

**6. Paired comparison by hand.** Per-task differences, candidate minus reference, in points: T1 0, T2 +66.7, T3 −33.3, T4 0, T5 +66.7, T6 0; the mean is 100/6 = **+16.7 points**. By majority (two of three runs): the reference is right on T1, T3 and T4; the candidate on T1, T2, T4 and T5. **b = 1** (T3: reference right, candidate wrong), **c = 2** (T2 and T5). Exact McNemar: 2 × (C(3,0) + C(3,1)) / 2³ = 2 × 4/8, capped at 1: **p = 1.0**. Family means: **A +33.3, B −16.7, C +33.3**.
- With three families, a cluster bootstrap resample is one of only a few mixes of these three means. Its interval runs from −16.7 (every draw family B) to +33.3, and Lab 10.1's `compare` gives exactly that.
- What it cannot be is evidence of a difference: three independent families are far too few, and the percentile interval's ends are just the extreme family means. A strong answer says that with this little data both statistics say "cannot tell", and connects it to Chapter 7's power formula.

**7. Resume after a crash at the pull request.** Step by step: a new process opens the run store and restores the meter, plan position and history from the checkpoint, which was saved after `run_tests`. The policy re-issues `open_pull_request` with the same arguments. The boundary verifies the token, checks the budget and computes the diff's hash from the branch, then finds the approval already granted for these exact arguments, so it asks no one. The journal holds a step with this call's idempotency key (the run and the branch) whose outcome is only `started`; the contract declares `idempotent=True`, so the handler runs again. It looks for an open pull request on `agent/ht-031`, finds 5100, and returns it with `existing: True` without creating anything. The step is recorded `ok`, and the run finishes with one pull request: Lab 10.2's drill D02.
- If the handler created without looking first, the same resume opens a **second pull request**; Lab 10.2's blind-handler run shows 2 pull requests and 2 creates. (Real GitHub would refuse a second open pull request for the same head and base with a 422 error, which the handler would then see as an error outcome.)
- If the contract declared `idempotent=False`, the boundary would refuse the call with `unknown_outcome`. The policy repeats it, and the third refusal stops the run as `repeated_failure:refused:unknown_outcome`, with pull request 5100 open but unrecorded: a person must check GitHub and close or adopt it. This is drill D03's path, there for a file edit.

## Design

**8. A reply-drafting assistant for support.** Marking notes. A strong answer:
- Starts from a workflow: retrieve documentation passages and the ticket's history (Chapter 2's retrieval), then one model call drafts a reply that cites its sources. An agent is justified only if a measured class of tickets needs searches the workflow cannot plan, such as several lookups that depend on each other, and then as a routed step.
- Lists tools with contracts: `search_docs` (read), `read_ticket` and `read_customer_history` (read, scoped to the ticket's workspace, with Chapter 14's redaction for personal data), `save_draft` (write, to the ticket's draft field only). It has no tool to send a reply and no general search over all tickets.
- Gives one identity with an owner (tomas.b, the support lead, is a natural owner), the narrowest scopes, 15-minute tokens and on-behalf-of the support engineer. It also gives a step, money and time budget from dev runs, and a repeated-failure rule.
- Treats ticket text as untrusted input (Chapter 2's TK32 injection ticket; Chapter 12), keeps it out of the instructions, and caps the task at autonomy tier T2 until injection defences are tested.
- Evaluates offline on labelled tickets with dev and held-out splits, a rubric or calibrated judge (Chapter 7), and paired comparison with the current process. Online, it uses shadow mode and then the engineers' edit distance and send rate.
- If the assistant could send replies itself, sending becomes an external, irreversible, customer-visible effect. It must be approval-gated per reply, bound to the exact text (T3), or never automated for tickets touching billing, access or security. The lethal trifecta (Chapter 3) applies, because it reads untrusted content, holds private data and can communicate externally.

**9. The live rerun ADR-027 requires.** Marking notes. A strong answer:
- Sizes the evaluation for the questions that decide the design. These are how often the workflow's context misses a file, and how often each design opens a wrong pull request, not overall success. It uses Chapter 7's power formula with a disagreement rate from a pilot; the lab's 5.6% suggests about 173 tasks for a 5-point difference, so 90 tasks are not enough. It reports McNemar beside every interval, and it corrects for, or at least states, the number of comparisons.
- Chooses tasks from Relay's real backlog with approved tests, grouped into families by spec change, split into dev and held-out by family, with the held-out split run once after every decision.
- Judges success without hidden tests: hold back part of each task's acceptance tests from the helper, written by the spec's authors, plus blind human review of each pull request against the spec. It measures reviewer agreement (Chapter 7's kappa) on a sample.
- Measures success, wrong pull requests, cost, latency, refusals, approvals and stop reasons, with paired intervals that resample families and McNemar beside them.
- Costs it before running: tasks × designs × runs × measured cost per run at the dated price table. It has a hard ceiling in the harness (as the live adapter's $0.50 per call), and the incident's lesson that a budget is enforced by code, not by a dashboard.
- States the reversal conditions in advance. If the routed design's wrong-PR advantage disappears, prefer the simpler single agent. If the workflow's loss on cross-file tasks disappears, prefer the workflow. If budget stops exceed the ADR's threshold, recalibrate before deciding.

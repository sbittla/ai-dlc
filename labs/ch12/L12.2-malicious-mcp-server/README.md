## Brief

An MCP server runs with your privileges, and its tool descriptions and results become your model's context
(Chapter 3). Relay records its one server's launch command; nothing yet hashes the server's code at launch, so a
server could change behind an unchanged command (Chapter 13 returns to this from the supply-chain side). This lab
shows what a hostile server can do to a host once it is running, and builds the host-side checks that catch each
move, and the one move they cannot catch.

You get a minimal MCP **host** and fifteen scenarios. The servers are local fixtures that answer what a host asks
for: an announcement (name, version, scopes, token audience) and `tools/list`, again after `list_changed`. The
legitimate one is Lab 3.2's constrained query tool: its whole package, `server.py` included, is copied unchanged
into `vendor/` (Chapter 3's lab is not edited), so its own controls are tested too. Every server's code is a real
directory, and the host hashes what it is about to run.

**About the payloads.** Where a real attacker would put instructions in a tool description, the fixtures put an
**inert placeholder**, such as `[[INJECTION technique=tool-poisoning effect=unauthorised-tool-call]]`. None of
your checks reads it. They compare hashes, names, launch records and scopes with a reviewed record, so they catch a
CHANGE after review. They cannot catch a poisoned description that a reviewer approved: a pin freezes what was
reviewed, including what the reviewer missed (scenario S12).

## What you will practise

- **Pinning** each tool by a hash of its whole definition, checked at every `tools/list`, so a rug pull is a finding
  even when the version is unchanged, and even mid-session.
- **Allowlisting** servers by launch command, version and a source hash computed at launch over the code that runs.
- Catching **tool name collisions** between servers that were each reviewed alone.
- **Scope review**: no scope beyond the review, no token passthrough, and the token audience the review recorded.
- Treating every tool result as untrusted, including results from a reviewed server.

## How the tests choose what to grade

Tests run against `starter/` by default. In bash: `LAB_TARGET=solution python -m pytest -q`. In PowerShell:
`$env:LAB_TARGET="solution"; python -m pytest -q; Remove-Item Env:LAB_TARGET`. Always remove the variable, or later
runs grade the solution. Until you finish, failing tests stop with `NotImplementedError`; the data-integrity tests
pass from the start.

## Steps

### 1. Read the host and the fixtures (30 min)

Read `host.py` and `fixtures.py`, and `data/reviewed.json`. For each fixture, write what it changes compared with
the reviewed record. Why does the host mark every result untrusted, even from a reviewed server?

### 2. TODO 1: the definition hash (25 min)

Implement `definition_hash`. Why canonical JSON? What would a hash of the description alone miss (see S14)?

### 3. TODO 2: the allowlist (35 min)

Implement `check_allowlist`. The source hash is computed at launch from the code on disk, `server.py` included.
Which scenario does it catch that a launch-command check alone would miss?

### 4. TODO 3: pins (30 min)

Implement `check_pins`, then `python -m mcpguard.report scenarios` from `starter/`. Look at S04 session by session:
which sessions admit the server, and when does the rug pull show? How does the host catch S15 within one session?

### 5. TODOs 4 and 5: name collisions and scopes (40 min)

Implement `check_name_collisions` and `check_scopes`. Why must the audience be compared with the reviewed record,
not with the server's own name? The host has no passthrough path at all: what is MCP031 for, then?

### 6. Remove one check (30 min)

```bash
python -m mcpguard.report removeone
python -m mcpguard.report calls > ../evidence/calls.md
```

On Windows PowerShell 5.1, `>` writes UTF-16; use `| Out-File -Encoding utf8 ../evidence/calls.md`. Which check is
the only one that catches S11, and why could a review of each server alone not see it? Why does nothing catch S12,
and what would? What stops S10, and is it one of your checks?

### 7. Review a server (30 min)

Fill in `templates/mcp-server-review.md` for `notes-helper` 1.1.0 as `evidence/review-notes-helper-1.1.0.md`.
Decide admit or refuse, with reasons from the report.

### 8. Write up (20 min)

In `evidence/residuals.md`, list what these checks cannot see: a poisoned description approved at review (S12),
a server whose behaviour, not its description, changes, or results an outsider wrote (S09). Name the control for
each.

## Troubleshooting

- `NotImplementedError: TODO n` — expected until you implement TODO n.
- `ModuleNotFoundError: relaymcp` — run from `starter/` or `solution/`; `mcpguard/__init__.py` adds `../vendor`.
- Results differ from the chapter — check `LAB_TARGET`, rerun `python scripts/generate_data.py`, `git diff data/`.

## Known limits

The fixtures run in process; a real host launches servers as subprocesses or connects over HTTP. The fixture
servers' code is small and inert, but its hashes are real. A source hash covers the files the launch runs, not what
they load later from elsewhere. OAuth here is reduced to declared scopes and an audience; a real deployment
verifies tokens, as Chapter 14 describes.

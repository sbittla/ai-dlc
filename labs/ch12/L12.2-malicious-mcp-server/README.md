## Brief

An MCP server runs with your privileges, and its tool descriptions and results become your model's context
(Chapter 3). Chapter 13 pinned Relay's one server by its launch command and noted the gap: nothing hashed the
server's code at launch, so a server could change behind an unchanged command. This lab shows what a hostile server
can do to a host once it is running, and builds the host-side checks that catch each move.

You get a minimal MCP **host** and eleven scenarios. The servers are local fixtures that answer what a host asks
for: an announcement (name, version, scopes, token audience) and `tools/list`. The legitimate one is Lab 3.2's
constrained query tool, vendored unchanged in `vendor/` (a copy; Chapter 3's lab is not edited), so its own
controls are tested too.

**About the payloads.** Where a real attacker would put instructions in a tool description, the fixtures put an
**inert placeholder**, such as `[[INJECTION technique=tool-poisoning effect=unauthorised-tool-call]]`. None of
your checks reads it. They compare hashes, names, launch records and scopes with a reviewed record, which is how
they would catch a real description they cannot judge for meaning.

## What you will practise

- **Pinning** each tool by a hash of its definition, so a rug pull is a finding even when the version is unchanged.
- **Allowlisting** servers by launch command, version and a source hash computed at launch.
- Catching **tool shadowing**: two servers offering one tool name.
- **Scope review**: no scope beyond the review, no token passthrough, and a token audience that is the server.
- Treating every tool result as untrusted, including results from a reviewed server.

## How the tests choose what to grade

Tests run against `starter/` by default. In bash: `LAB_TARGET=solution python -m pytest -q`. In PowerShell:
`$env:LAB_TARGET="solution"; python -m pytest -q; Remove-Item Env:LAB_TARGET`. Always remove the variable, or later
runs grade the solution. Until you finish, failing tests stop with `NotImplementedError`; the data-integrity tests
pass from the start.

## Steps

### 1. Read the host and the fixtures (30 min)

Read `host.py` and `fixtures.py`, and `data/reviewed.json`. For each fixture, write what it changes compared with
the reviewed record. Why does the host mark every result untrusted, even from a reviewed server?

### 2. TODO 1: the definition hash (25 min)

Implement `definition_hash`. Why canonical JSON? What would a hash of the description alone miss?

### 3. TODO 2: the allowlist (35 min)

Implement `check_allowlist`. The source hash is computed at launch from the code on disk. Which scenario does it
catch that a launch-command check alone (Chapter 13's SC008) would miss?

### 4. TODO 3: pins (30 min)

Implement `check_pins`, then `python -m mcpguard.report scenarios` from `starter/`. Look at S04 session by session:
which sessions admit the server, and when does the rug pull show?

### 5. TODOs 4 and 5: shadowing and scopes (40 min)

Implement `check_shadowing` and `check_scopes`. MCP's security guidance says a server must not accept a token
issued for another audience. Which finding would a passthrough request also raise, and why both?

### 6. Remove one check (30 min)

```bash
python -m mcpguard.report removeone
python -m mcpguard.report calls > ../evidence/calls.md
```

On Windows PowerShell 5.1, `>` writes UTF-16; use `| Out-File -Encoding utf8 ../evidence/calls.md`. Which check is
the only one that catches S11, and why could a review of each server alone not see it? What stops S10, and is it
one of your checks?

### 7. Review a server (30 min)

Fill in `templates/mcp-server-review.md` for `notes-helper` 1.1.0 as `evidence/review-notes-helper-1.1.0.md`.
Decide admit or refuse, with reasons from the report.

### 8. Write up (20 min)

In `evidence/residuals.md`, list what these checks cannot see: for example a reviewed server whose code reads its
descriptions from a remote source after launch, or results an outsider wrote (S09). Name the control for each.

## Troubleshooting

- `NotImplementedError: TODO n` — expected until you implement TODO n.
- `ModuleNotFoundError: relaymcp` — run from `starter/` or `solution/`; `mcpguard/__init__.py` adds `../vendor`.
- Results differ from the chapter — check `LAB_TARGET`, rerun `python scripts/generate_data.py`, `git diff data/`.

## Known limits

The fixtures run in process; a real host launches servers as subprocesses or connects over HTTP, and would compute
the source hash from the installed files before starting the process. notes-helper's and analytics-readonly's source
hashes are labelled stand-ins. OAuth here is reduced to declared scopes and an audience; a real deployment verifies
tokens, as Chapter 14 describes.

## Brief

In October a coding agent built Relay's first escalation-rules feature exactly as its ticket said, and the ticket was wrong. Chapter 4 tells the story. The ticket had been summarised from three interviews that nobody went back to.

The product owner, lena.k, is starting again from the sources. You have her one-paragraph brief, three interview transcripts and five pages of Relay's documentation, all in `data/sources/`. You also have the first draft PRD a chat assistant produced from them (`data/prd-draft.md`), unedited.

You have three jobs.

1. **Build a small requirements checker** that a machine can run on every PRD change: provenance (is every quote really in its source?), vague and untestable statements, Given/When/Then criteria, contradictions, hidden dependencies, NFR coverage and traceability.
2. **Write the PRD** for escalation rules: problem, users, scope, constraints, risks, measurable goals, decisions, functional requirements and non-functional requirements, including security and abuse cases. Every requirement links to a source.
3. **Get it approved** by a named product owner, with a review record that says what the checker cannot tell you.

## Tracks

- **Builder:** do every step.
- **Leader:** steps 1, 2 and 4–7 are the core of your work, and are mostly writing in templates. The five functions in step 3 are 5 to 30 lines each. Implement them, or pair with a Builder. If you skip step 3, run steps 4–6 from `solution/` instead of `starter/`, and the rubric's 3 points for the checker are given for explaining the draft's findings in `evidence/prd-review.md` section 1 instead.

## What you will practise

- **Problem framing** with users, scope, constraints, risks and success measures that have a baseline and a target.
- **Elicitation with provenance:** every requirement carries a verbatim quote from a named source.
- Finding **ambiguity, contradictions, untestable statements and hidden dependencies** before an agent builds them.
- Writing **acceptance criteria a machine can check**, and NFRs for security, abuse, privacy, accessibility, operability, cost and human-AI interaction.
- **Traceability and change impact:** goal → requirement → decision → test, and what to re-review when a source changes.
- Treating **source documents as untrusted input**, including text addressed to AI assistants.

## Steps

### 1. Read the sources (25 min)

Read `data/sources/BRIEF.md`, then the three interviews, then the five `DOC-*` pages. For each interview, note what the person needs, what they assume Relay already has, and where they disagree with another source. Find the paragraph in one transcript that is addressed to AI assistants. Start `evidence/elicitation-log.md` from the template as you read.

### 2. Frame the problem (20 min)

Copy `templates/prd.md` to `evidence/prd.md`. Fill in Problem, Users, Scope, Constraints, Risks and Goals. Each goal needs a measure (what is counted, over which population and period, from which system), a baseline and a target. Ask: can Relay 4.17.2 measure the baseline today? If not, say what proxy you will use.

### 3. Implement the checker (50 min)

Implement the five TODO functions in `starter/reqcheck/checks.py`. Each docstring is the specification; `tests/test_checks.py` checks each on inputs you can verify by hand.

| Function | What it decides |
| --- | --- |
| `check_provenance` | Does each quote appear, word for word, in the source it names? Is it long enough to mean anything? |
| `find_vague_terms` | Which words in a statement or criterion could two engineers read differently? |
| `check_criteria` | Does every requirement have criteria, each in Given/When/Then form? |
| `find_contradictions` | Do two requirements set the same value differently? |
| `check_traceability` | Does every goal have a measure, baseline, target and requirement, and does every requirement cite known goals, decisions and requirements? |

```bash
python -m pytest -q tests/test_checks.py
python -m pytest -q
```

### 4. Check the assistant's draft (15 min)

```bash
cd starter
python -m reqcheck.report --sources ../data/sources --lexicon ../data/lexicon.json ../data/prd-draft.md --details > ../evidence/draft-check.md
```

On Windows PowerShell 5.1, `>` writes UTF-16; use `| Out-File -Encoding utf8 <file>` instead.

Pick the five findings that would have done most harm if an agent had built the draft. Look hard at ESC-R06: its quote is verbatim, so why is it the only critical finding? Then look for what the checker missed: read ESC-R01 against INT-1 and decide whether "the shift lead" is a role Relay has.

### 5. Write your PRD (50 min)

Write requirements, decisions and criteria in `evidence/prd.md` until the checker reports no open findings:

```bash
cd starter
python -m reqcheck.report --sources ../data/sources --lexicon ../data/lexicon.json ../data/prd-draft.md ../evidence/prd.md --details
```

Record every contradiction as a decision taken by the product owner, not by you or an assistant. Elicit at least two abuse cases and one security NFR. Write at least one human-AI interaction requirement: what does Relay show when the triage model suggests a priority, and who can override it?

**With a chat assistant (optional).** Give it the sources and the template, and ask for a draft. Treat its output exactly like `prd-draft.md`: run the checker, and check every quote yourself. Record what it produced in the elicitation log's AI-use section. Then, and only then, compare your PRD with `data/prd-v1.md`.

### 6. Traceability and change impact (10 min)

```bash
cd starter
python -m reqcheck.report --sources ../data/sources --lexicon ../data/lexicon.json ../evidence/prd.md --matrix --impact INT-3
python -m reqcheck.report --sources ../data/sources --lexicon ../data/lexicon.json ../evidence/prd.md --impact ESC-R02
```

Which source, if it changed, would force you to re-review the most tests? Why?

### 7. Review and approval (10 min)

Complete `templates/prd-review.md` in `evidence/`. Ask a colleague or your instructor to act as product owner and approve the PRD: their name goes in both `Product owner` and `Approved by`. It must not be your name if you wrote it, and it can never be an agent's. Then run the gate:

```bash
cd starter
python -m reqcheck.report --sources ../data/sources --lexicon ../data/lexicon.json ../evidence/prd.md --fail-on low; echo "exit $?"
```

In PowerShell, use `echo "exit $LASTEXITCODE"`.

## Sample of acceptable evidence (excerpt)

> The assistant's draft (v0.1) has 50 open findings: 1 critical, 17 high and 32 medium. Three pairs of requirements contradict each other: the first P1 step (15 against 10 minutes), who edits rules (Members against Admins) and whether the model's P1 starts escalation. Fourteen findings are hidden dependencies, mostly on task priority and acknowledgement, which Relay 4.17.2 does not have. ESC-R03's quote, "after thirty minutes it should go to the workspace Owner", is not in INT-1: the customer said "the person who owns the queue". The only critical finding is ESC-R06, whose quote is verbatim, but comes from pasted text addressed to AI assistants: the SMS "agreement" was never made. The checker cannot tell whether a verbatim quote was understood correctly, so every decision was read back to its source's author.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| A verbatim quote reported as RQ003 | Curly quotes or apostrophes copied from a word processor. The sources use straight ASCII quotes. |
| `RQ003` on a quote that spans two lines of a transcript | Fine in the reference: `normalize()` collapses whitespace. Check you call it on both the quote and the source. |
| "fast" flagged inside "breakfast" | Use `term_pattern()`; it matches whole words and phrases only. |
| Too many RQ030 findings | One finding per pair of requirements whose values differ, not per requirement. Equal values are not contradictions. |
| `RQ041` everywhere | A requirement that mentions P1 depends on the requirement that introduces task priority. List it under `Depends on:`. |
| `RQ012` on an NFR with a number | The number needs a unit (`10 minutes`, `95%`), or use `at most 20`, a named standard such as `WCAG 2.2`, or `must not`. |
| Your PRD parses with no requirements | Field names are case-sensitive and each item needs a `### ID — title` heading (with an em dash) under `## Requirements`. |

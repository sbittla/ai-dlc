## Brief

Two scenarios, both on generated telemetry. The opening incident of Chapter 16: on 2 February 2027 an incident
assistant blamed the 15:00 deploy while a credential-stuffing attack saturated the database. The game day of
Thursday 18 February 2027: database latency (F1) and a suspicious export pattern under a game-day agent identity (F2),
with responders on call.

You will build the parts of incident response that Chapter 16 says must not rest on confidence: a citation check for
the assistant's hypotheses, the remediation gate, per-fault measures, and a postmortem checker. Then you replay the
game day through Relay 4.27.0's own detection, SLO, routing and paging code and write its postmortem.

**About the data.** Everything in `data/` is **generated** by `scripts/generate_data.py` and labelled. The attack, the
faults, the responders' actions and their timings were configured; the **incident assistant is simulated**, and its
answers, including its mistakes, were written into the data. The results show what the checks and the gate do with
these inputs, not how real models or responders behave. `vendor/relay/` is a copy of Relay 4.27.0's `relay.telemetry`
and `relay.audit` from Lab 16.1, and `vendor/config/` its rule and routing files; the generator refreshes both. The
person-proof key in `data/people.json` is published and worthless outside the lab.

## What you will practise

- Treating an AI root cause as a **hypothesis**, and checking its **citations** as of the moment it was made.
- An **approval-gated** remediation path that authenticates people and audits every refusal.
- Running and measuring a **game day**.
- Writing a **blameless postmortem** whose action items change specs, tests, evaluations and detection.

## How the tests choose what to grade

Tests run against `starter/` by default. In bash: `LAB_TARGET=solution python -m pytest -q`. In PowerShell:

## Steps

### 1. Read (15 min)

Read Sections 16.4 and 16.5 and ADR-039 (in Lab 16.1's `relay-repo/docs/adr/`). Open
`data/incident-2027-02-02/assistant-v0.json`: what evidence did the assistant give?

### 2. The citation check: TODO 1 (60 min)

Implement `check_citation` and `check_hypothesis` in `starter/gameday/citations.py`. The module docstring defines
each assertion; `Store` hides everything after its `as_of` and owns the baseline and the cause-to-mechanism map.
`tests/test_todos.py` has hand-checked fixtures, including three ways a model could game a weaker check: a
mechanism cited for another cause, no citations at all, and a causal claim labelled as an attribution.

### 3. Judge the incident's hypotheses (20 min)

```bash
cd starter
python -m gameday.report incident
python -m gameday.report hypotheses > ../evidence/hypotheses.md
```

On Windows PowerShell 5.1, `>` writes UTF-16; use `| Out-File -Encoding utf8 ../evidence/hypotheses.md` instead. What
was H0's verdict when the rollback was approved, and when did it become contradicted? Which supported hypothesis was
available at 15:18? How many minutes earlier would the security on-call have been paged with 4.27.0's rules?

### 4. The remediation gate: TODO 3 (50 min)

Implement `Gate.decide` in `remediate.py`. Every refusal must be audited before it is raised. Read `Gate.request`
and `matches` first: requests are authenticated and name a hypothesis, which the gate checks itself; it must be
supported and about the action, or an agent is refused and a person needs an incident ID and a reason. Why may
the requester of a two-person action be one of the two, but never approve a one-person action? Why is each proof
bound to one request and usable once? Why can no proof make the assistant an approver or a kill-switch tripper?

### 5. Per-fault measures: TODO 2 (25 min)

Implement `fault_measures` in `timeline.py`.

### 6. Replay the game day (25 min)

```bash
python -m gameday.report gameday > ../evidence/gameday.md
```

Which alert paged first for F1, and why before the latency objective? Why did the gate refuse the assistant's restart?
Why did DR-002's page escalate twice? What did the planted text in export job 3 make the assistant propose, and what
stopped it? Which five refusals did the gate audit?

### 7. The postmortem checker: TODO 4 (25 min)

Implement `check` in `postmortem.py`, then `python -m gameday.report postmortem`. Read the agent's draft and the team's
version side by side. Which findings are about blame, and which about evidence?

### 8. Write the game day's postmortem (20 min)

Copy `templates/postmortem.md` to `evidence/postmortem-2027-02-18.md` and write it from the game-day report. Every
timeline line cites an alert, an event or a gate record. Include at least four action items of different types, one of
them an adversarial evaluation case for the planted text. Check it:

```bash
python -c "from gameday.postmortem import check; import json; p=json.load(open('../data/people.json'))['people']; print(check(open('../evidence/postmortem-2027-02-18.md', encoding='utf-8').read(), sorted(p)))"
```

It must print `[]`.

## Sample of acceptable evidence (excerpt)

> At 15:18, when the rollback was approved, the deploy hypothesis cited only timing and was unsupported; at 15:41 it was
> contradicted, because slow requests stayed 206 times their baseline after the rollback. The sign-in hypothesis was
> supported at 15:18: failed sign-ins rose more than tenfold first, and sign-in writes took 83.1% of database time. In
> the game day the worker's stall paged at 14:17, before the latency objective at 14:23; the gate refused the
> assistant's restart because its hypothesis was unsupported, and refused the planted restore at 14:41.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| Every citation is `unresolved` | `_known` was not used, or the window is outside `as_of`. |
| H1 is supported | `dominates` compares the mean share over the window with `share`; the notifications' share is tiny. |
| H0 is contradicted at 15:18 | `counter_evidence` must run on the store as of 15:18, when the rollback was not done yet. |
| A refusal is missing from the audit | Call `refuse`, which audits and raises; do not raise `Refused` directly. |
| The failover is approved by priya.n alone | Two-person actions need two distinct people whose roles cover both listed roles. |
| A good proof is refused as `proof_not_for_this` | Decision proofs carry the request ID and the request's args SHA-256; check both. |
| A supported hypothesis is refused for a rollback | It must be a cause hypothesis whose cause is `event:<the deploy>`; H2 and H3 are about sign-ins. |
| `check` reports PM006 for a timeline line | PM006 reads only the Contributing factors section. |
| `test_vendored_relay_is_lab_16_1s_copy` fails | Lab 16.1's telemetry changed; run `python scripts/generate_data.py` here. |

## Known limits

- The assistant is simulated. A live incident assistant needs its own registry entry (`incident-assistant`) and
  identity before it runs, and an evaluation set; neither is in 4.27.0.
- The citation check verifies what is cited, not whether the right thing was cited.
- Person and agent proofs are HMACs under a published lab key, standing in for a real identity provider's signed
  tokens. The gate is not in Relay's `src/` yet (ADR-039).

## Brief

Relay needs an HTTP service and a background triage worker, and Chapter 4's escalation rules need both. In May a three-person sub-team rejected a microservices design in a meeting and wrote nothing down. In November an agent proposed it again. Chapter 6 tells the story.

You have Chapter 4's NFR catalogue and decisions as architecture drivers (`data/drivers.json`), three architecture options described as components and flows (`data/options/`), an agent's draft decision record and an agent's draft threat model. You also have **Relay 4.19.0** in `relay-repo/`: the teaching snapshot's HTTP service and the triage worker that production Relay has run since May, which later chapters deploy, load-test and observe.

You have four jobs.

1. **Build a small scoring and checking tool**: weighted scores with must-have drivers, a ranking with a stated tie rule, a one-weight-at-a-time sensitivity check, an ADR checker and a threat-model checker.
2. **Score the three options** (modular monolith with a worker, microservices, and the monolith with one separate triage service) against the drivers, and say where the scores are judgement rather than fact.
3. **Write the decision record** (ADR) and **one threat model per option**, with trust boundaries on every diagram, until both pass the checker's gate.
4. **Run Relay 4.19.0**: start the service and the worker, submit a ticket twice with the same idempotency key, and read the suggestion.

## What you will practise

- Turning NFRs and constraints into **weighted architecture drivers**, and separating the significant ones.
- **Comparing options** with explicit, reviewable scores, a tie rule that favours the simpler option, and a sensitivity check.
- **Structural counts** that are facts, not judgements: deployable units, databases, trust boundaries, components on a critical path, and availability in series (Equation 6.1).
- **Decision records** with rejected alternatives, links to PRD decisions D1–D9 and NFR IDs, and a named architect.
- **Lightweight threat models** for every option, with STRIDE at each trust boundary and evidence for each control.

## Steps

### 1. Read the drivers (15 min)

Read `data/drivers.json` beside Chapter 4's PRD (`labs/ch04/L4.1-brief-to-prd/data/prd-v1.md`). For each driver, decide whether the choice of architecture changes how well Relay can meet it. Two have weight 0. Do you agree with both? Which weights would you change, and would the architect of record (sam.o) need to agree?

### 2. Implement the scorer (40 min)

Implement TODO 1–3 in `starter/archscore/scoring.py`. The docstrings are the specification; `tests/test_scoring.py` checks each on inputs you can verify by hand.

| Function | What it decides |
| --- | --- |
| `weighted_score` | The option's total and the maximum possible, over significant drivers |
| `rank` | Best first; a must driver scored 0 disqualifies; on a tie, the option with fewer deployable units wins |
| `weight_to_flip` | For each driver, the nearest weight from 0 to 5 that would make the runner-up win |

```bash
python -m pytest -q tests/test_scoring.py
```

### 3. Score the options (10 min)

```bash
cd starter
python -m archscore.report score --drivers ../data/drivers.json ../data/options/A-modular-monolith.json ../data/options/B-microservices.json ../data/options/C-monolith-plus-triage-service.json --details
python -m archscore.report score --drivers ../data/drivers.json ../data/options/A-modular-monolith.json ../data/options/B-microservices.json ../data/options/C-monolith-plus-triage-service.json --explain availability
python -m archscore.report score --drivers ../data/drivers.json ../data/options/A-modular-monolith.json ../data/options/B-microservices.json ../data/options/C-monolith-plus-triage-service.json --scenario ../data/scenarios/five-teams.json
```

On Windows PowerShell 5.1, `>` writes UTF-16; use `| Out-File -Encoding utf8 <file>` to save a report.

Separate facts from judgements. The structure table is counted from the option files; every score is a person's judgement with a reason. The report's sensitivity lines say how many one-point score changes would reverse each comparison: read the A-against-C lines closely. Pick the three scores you trust least, change them in a copy of the option file, and rerun. Does the ranking move? Then read the scenario: what would have to be true for Option C or Option B to win? Ideally a second person scores the options independently before you compare.

### 4. Implement the checkers and check the drafts (30 min)

Implement TODO 4–5 in `starter/archscore/checks.py`, specified by `tests/test_checks.py`. Then:

```bash
cd starter
python -m archscore.report adr --drivers ../data/drivers.json ../data/adr/ADR-007-draft.md --gate; echo "exit $?"
python -m archscore.report threats --options ../data/options ../data/threat-models/A-draft.md --gate; echo "exit $?"
```

In PowerShell, use `echo "exit $LASTEXITCODE"`.

The draft ADR rejects microservices because they are "too complex for now", with no condition for revisiting. Why is that not a reason a future reader can test? Which two of its links point at IDs that do not exist? Which trust boundary did the draft threat model leave out?

### 5. Write the ADR and three threat models (75 min)

Copy `templates/adr.md` to `evidence/ADR-007.md` and write the decision from your scores. Consider at least four options: the three you scored and one that fails a must driver, which you need not score (Chapter 6, Section 6.2, lists candidates). Every rejected option needs a reason of at least eight words, in terms of the drivers, and a `Revisit if:` line.

ADR009 accepts only names in `people` in `data/drivers.json` (aisha.r, lena.k, priya.n, sam.o, tomas.b). Write `Decided by: sam.o`, the architect-of-record role your approver plays, and record in `evidence/architecture-review.md` who actually approved, and how. Never write an agent's name or your own.

Copy `templates/threat-model.md` three times, to `evidence/threat-model-A.md`, `-B.md` and `-C.md`. Every boundary in the option file appears in the diagram and has at least one STRIDE threat with a control and evidence. For Option A, cite tests in `relay-repo/tests/` where they exist. For Options B and C, little or nothing is built, so say what work each control would need. A test proves a control only against the threat it exercises: import rules, for example, cannot constrain a compromised process.

```bash
cd starter
python -m archscore.report adr --drivers ../data/drivers.json ../evidence/ADR-007.md --gate
python -m archscore.report threats --options ../data/options ../evidence/threat-model-A.md ../evidence/threat-model-B.md ../evidence/threat-model-C.md --gate
```

Work until both gates pass. Then compare with `relay-repo/docs/adr/ADR-007-modular-monolith-async-triage.md` and `data/threat-models/`.

### 6. Run Relay 4.19.0 (10 min)

Two terminals, from `relay-repo/`. Bash:

```bash
PYTHONPATH=src python -m relay.service --db relay.db --demo --port 8080
curl -s localhost:8080/healthz
curl -s -X POST localhost:8080/v1/triage-jobs -H "Authorization: Bearer demo-member" \
     -H "Idempotency-Key: ticket-0001" -d '{"text": "We were charged twice for October"}'
PYTHONPATH=src python -m relay.worker --db relay.db --drain
curl -s localhost:8080/v1/triage-jobs/1 -H "Authorization: Bearer demo-member"
```

PowerShell: set `$env:PYTHONPATH="src"` once (remove it afterwards with `Remove-Item Env:PYTHONPATH`). Use `curl.exe`, not `curl` (an alias for `Invoke-WebRequest` in Windows PowerShell 5.1), and put the body in a file to avoid quoting problems: `curl.exe -s -i -X POST localhost:8080/v1/triage-jobs -H "Authorization: Bearer demo-member" -H "Idempotency-Key: ticket-0001" --data-binary "@ticket.json"`, where `ticket.json` holds `{"text": "We were charged twice for October"}`. `-i` shows the `Idempotent-Replayed` header. `Invoke-RestMethod` hides response headers and throws on 422; in PowerShell 7, `Invoke-WebRequest -SkipHttpErrorCheck` shows both.

Submit the same ticket twice with the same key, then once with the same key and different text. What status codes do you get? Stop the worker for more than five minutes and read `/healthz` again. The `demo-*` tokens open a local demo and nothing else, and `--demo` refuses any `--host` other than 127.0.0.1, ::1 or localhost. Run `python -m pytest -q` in `relay-repo/` (88 tests) and `python tools/lint.py`.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `KeyError` from `weighted_score` | The option has no score for a driver with weight above 0; weight-0 drivers need none. |
| `weight_to_flip` returns a weight that only ties | "Win" means strictly greater; a tie goes to the simpler option, so it is not a flip. |
| ADR006 on a reason you wrote | The reason must be on one line starting `Rejected because:`, directly under the `### Option X — …` heading. |
| ADR005 for the chosen option | The Decision section must name it exactly as `Option A`. |
| TM006 although the diagram shows the boundary | The diagram must contain the boundary's ID (`TB2`), not only its description. |
| `ModuleNotFoundError: relay` when running the service | Run from `relay-repo/` with `PYTHONPATH=src`. |
| `database is locked` | Two workers on one database file under heavy load; the queue waits up to 5 seconds. Use separate `--worker-id`s and retry. |
| Em dashes print as `?` or garbled | Your console's encoding; save with `Out-File -Encoding utf8` and open in an editor. |

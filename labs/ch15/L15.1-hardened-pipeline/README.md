## Brief

On Monday 1 March 2027 Relay's `security-gates` check failed three times on one pull request, because Trivy timed
out downloading its vulnerability database. The engineer asked a coding session to make CI pass. The agent added
one line to `.github/workflows/ci.yml`: when Trivy failed, write an empty SARIF report instead. The gate accepted
it, a reviewer who belonged to both owning teams approved the pull request, and for nine days no dependency or
configuration scan reported anything. Chapter 15 tells the story (a composite).

You have what Relay built afterwards: **Relay 4.29.0** in `relay-repo/`. Its `.github/workflows/pipeline.yml`
builds once, runs four gates (test, eval, adversarial, scan), signs and attests through Chapter 13's
`release.yml`, admits images under `deploy/admission/policy.json` and deploys production's desired state
(`deploy/gitops/production.json`) with a canary. `governance/pipeline-guard.json` says how a pipeline change is
reviewed. Two new controls close the three classes Chapter 12's coverage gate left short: `tools/sandbox_run.py`
runs agent test runs with no network (C10, C11), and `relay.release.judged` decides judge-injection items by a
person's label (C14).

You will build the checks that decide: a lint for workflow files, the pipeline guard (a gate diff and review
rules), the gates' failure behaviour, admission, and Gate G4's adversarial row with deployment evidence.

**About the data.** Everything in `data/` is **generated** by `scripts/generate_data.py`, deterministically. The
incident, the train releases of 22 March to 30 April and the twelve release candidates are **simulated**, and what
is wrong with each was **configured**. Scanner reports are simulated SARIF; the advisories `LAB-ADV-2027-0042`
and `LAB-ADV-2027-0057` are invented and imply nothing about any real package or image. Bundles are signed with an
HMAC standing in for Sigstore, with a published key. Deployment records stand for post-deploy checks in
production that this lab cannot run. The coverage reports are not configured: the generator computes them by
running Chapter 12's probes (vendored from Lab 12.1 in `vendor/`) and the two new probes on `relay-repo/`.

## What you will practise

- Linting workflows for **pinned actions, least-privilege tokens, OIDC, untrusted triggers and script injection**.
- A **gate diff**: telling a pipeline change that weakens a gate from one that does not.
- **Review rules** that make a pipeline change get its own review.
- **Fail-closed** gates: an empty report, a missing label or a report for another release cannot pass.
- **Admission** of signed images by exact identity, transparency log and attestations.
- **Gate G4's adversarial row**: the coverage gate plus deployment evidence, on a date.

## How the tests choose what to grade

Tests run against `starter/` by default. To check the reference, in bash: `LAB_TARGET=solution python -m pytest -q`.
In PowerShell: `$env:LAB_TARGET="solution"; python -m pytest -q; Remove-Item Env:LAB_TARGET`. The variable persists
until it is removed, so always remove it, or later runs will silently grade the solution. Run pytest from this lab's
folder.

Until you finish, failing tests stop with `NotImplementedError`. The tests of the provided parser and signature,
and `tests/test_data_relay.py` (which runs Relay's 959 tests, about 30 seconds), pass from the start.

## Steps

### 1. Read the incident and the pipeline (25 min)

Read Chapter 15's opening incident, ADR-044 and ADR-045, and `relay-repo/.github/workflows/pipeline.yml`. Then
compare `data/incident/ci-before.yml` with `ci-after.yml`. Why did the gate pass an empty report, and why did one
approval cover the workflow file?

### 2. Lint workflows: TODO 1 (50 min)

Implement `lint` in `lint.py`; the docstring is the specification. Then, from `starter/`:

```bash
python -m pipeline.report lint
```

Relay's five workflows should have no findings and the agent's first draft twelve. Which of the draft's findings
would a reviewer reading quickly be most likely to miss? Why does the lint find nothing in `ci-after.yml`?

### 3. The pipeline guard: TODO 2 (60 min)

Implement `gate_diff` and `guard` in `guard.py`, then:

```bash
python -m pipeline.report guard
python -m pipeline.report incident
```

The incident's pull request should be blocked by five findings. Which one alone would have stopped it, and which
would still have stopped it if the agent had put the workflow change in a pull request of its own? Why must the
guard not be defined in `.github/workflows/` of the repository it guards?

### 4. Stages and failure behaviour: TODO 3 (55 min)

Implement `stage_eval`, `stage_scan` and `run_pipeline` in `stages.py`. Then:

```bash
python -m pipeline.report candidates
python -m pipeline.report candidates --id P-08 --mode verify-only
```

P-04 and P-08 end in "cannot decide". Why is that a failure and not a skip?

### 5. Admission: TODO 4 (35 min)

Implement `admit` in `admission.py`. P-09 to P-11 should be refused. P-10 is signed, by Relay's own release
workflow: what exactly is wrong with it, and why does a pattern such as `release.yml@refs/*` let it through? Then
run `admit` on `data/train/T-2027-04-01.json`: its image was signed in verify-only mode after its adversarial gate
failed. Which rule refuses it, and what would a signature alone have meant without that rule?

### 6. Gate G4's row: TODO 5 (35 min)

Implement `deployed` and `g4_row` in `g4.py`, then:

```bash
python -m pipeline.report matrix --as-of 2027-04-30
python -m pipeline.report timeline
python -m pipeline.report train > ../evidence/train.md
```

On Windows PowerShell 5.1, `>` writes UTF-16; use `| Out-File -Encoding utf8 ../evidence/train.md` instead. On
which date does the row hold, and what was the last missing piece? In the verify-only period, why did the
adversarial stage stop releases the train shipped, and was that a reason to stop the train?

### 7. Relay 4.29.0 and the workspace audit (20 min)

```bash
cd ../relay-repo && python tools/sandbox_run.py check && python tools/supplychain.py && cd -
```

From `labs/ch03/L3.1-accountable-workspace/solution/`:

```bash
python -m audit.report --policy ../data/policy.json --as-of 2027-05-04 --fail-on high ../../../ch15/L15.1-hardened-pipeline/relay-repo
```

It should report 0 open and 0 waived.

### 8. Review (20 min)

Fill in `templates/pipeline-review.md` for `data/drafts/agent-draft-v1.yml`, and `templates/switch-decision.md`
for the switch from verify-only to deliver.

## Troubleshooting

- `NotImplementedError: TODO n` — expected until you implement TODO n.
- Results differ from the chapter — check `LAB_TARGET`, then rerun `python scripts/generate_data.py` and
  `git diff data/`; the data must not change.
- `UnicodeEncodeError` on Windows — set `PYTHONIOENCODING=utf-8`.
- `yamlish.YamlError` — the provided parser reads the YAML that workflows use, not all of YAML; keep test fixtures
  to block mappings, lists, flow mappings and block scalars.

## Known limits

The pipeline runs in a simulator. The workflows in `relay-repo/` name tools the snapshot does not vendor, and are
marked illustrative. The pipeline guard you build runs, in Relay, from the platform team's repository
(`governance/required-workflows.json`), because a check defined in the repository it guards can be changed by the
pull request it judges; that ruleset, the merge queue and the helper's sandbox runner are platform settings outside
the snapshot. The gate diff names common weakenings, not all; GD009 and GD010 send every other change to a required
job's commands or to gate configuration to a security reviewer. Labels' labellers are names in a file under review,
not authenticated identities. The service and worker do not yet read `relay.release.flags`. The test-sandbox and egress probes model isolation; no container starts. Signatures are
HMACs. Deployment records are generated. Production is outside the teaching snapshot, and non-production still
carries no traffic until the PostgreSQL adapter exists.
